# {代码语言} Bug 修复全流程 SOP
## 通用注释要求
- 涉及生成或修改代码时，每个函数 / 方法都必须添加注释，说明其功能和适用场景。
- 关键业务流程、复杂分支、异常处理、副作用、并发、权限、外部调用等关键部分必须添加必要注释。
- 注释必须沿用目标文件已有风格，保持简洁准确，避免重复描述代码本身。

> 当用户提出"修复XXX问题"、"这里有个bug"、"排查XXX异常"等 Bug 修复类请求时，严格按以下流程执行。
### 0. 交互开场范式（强制）
在首次响应或跨阶段切换时，**禁止全文复述 SOP**，但必须使用 **1 句状态 Header** 告知用户当前进展，例如：
- **澄清阶段开场**：`🤖 已进入 Bug 修复 SOP（当前：需求澄清）。为了快速定位，请先确认以下关键信息：`
- **分析阶段开场**：`📊 需求已确认，正在进行 Bug 分析与分级评估...`
- **调研阶段开场**：`🔍 正在进行多渠道调研与问题定位（GitHub 等站点不可直接访问时将自动降级）...`
- **修复阶段开场**：`🛠️ 根因已确认，准备开始编码修复（将遵循最小化改动原则）。`
- **关闭/延期开场**：`📋 经分析，此问题建议 [标记为观察 / 延期处理 / 非 Bug]，理由如下：`

## 前置：需求澄清协议（强制门控）
> ⚠️ **必问项未全部澄清前，禁止进入问题定位与代码修改阶段**，禁止以"我已经理解"为由跳过追问。

### 核心原则
#### 🚫 强制门控规则
1. 禁止在必问项未澄清时进入执行阶段（输出方案、写代码、生成报告等）
2. 禁止跳过自检环节 — 必须逐项对照问题清单完成信息充分度校验
3. 禁止一次性抛出所有问题 — 每轮最多提出 3~5 个最关键的问题
4. 允许合理推断 — 如果上下文已足够推断出答案，可表述为"我理解为 XXX，如有偏差请纠正"，无需反复追问

#### ✅ 智能退出条件
当以下条件**全部满足**时，自动结束澄清流程，进入正式修复阶段：
- 所有 🔴 必问项已有明确答案（用户提供或可合理推断）
- 🟡 选问项中没有会严重影响修复质量的遗漏

### 执行流程
1. **信息自检**：内部对照 `reference/clarify-checklist.md` 中的 Bug 修复专属问题清单，标记已知/未知/可推断项
2. **结构化追问**：将未知必问项 + 高影响选问项组合为一轮追问（≤5个），附已理解信息
3. **循环确认**：用户答复后更新自检状态，最多 3 轮追问；剩余模糊点带假设推进并标注
4. **退出澄清**：输出需求理解确认，进入问题定位阶段

> 完整问题清单、追问话术、特殊场景处理详见：`reference/clarify-checklist.md`

## 阶段一：Bug 分析与分流
### 步骤 1：信息整理
承接需求澄清输出，梳理并确认核心要素：
- 问题现象（报错信息、异常行为）
- 复现条件（操作路径、数据条件、环境）
- 期望行为（正确结果是什么）
- 影响范围与紧急程度

定位过程中发现新的模糊点，可简要追问后继续。

### 步骤 2：Bug 分级与处置决策
> 🔑 **并非所有 Bug 都需要修复，也并非都需要深入排查。** 投入时间前先分级。

- **🟢 简单**：一眼能看出原因，改动 ≤ 2 行，影响孤立 → **快速路径**：跳过调研，直接修复
- **🟡 中等**：需追溯调用链，涉及多个文件 → **标准流程**：调研 → 定位 → 修复 → 验证
- **🔴 复杂**：并发/竞态/跨系统/偶现 → **完整流程**：深度调研 → 多方案对比 → 渐进修复

**处置决策**：能稳定复现 + 根因明确（🟢）→ 直接修复；否则进入步骤 3 调研。不能复现 + 影响严重 → 优先排查；不能复现 + 低影响 → 评估是否值得投入。

**分流出口**——以下场景标记 wont-fix / defer，输出理由等用户确认：
- 设计意图（非 Bug） / 无法复现+低影响 / 修复成本>>影响 / 上游依赖问题

> 完整分级表、决策树、分流场景详见：`reference/triage-guide.md`

### 步骤 3：多渠道调研
> 仅 🟡 中等和 🔴 复杂 Bug 执行。🟢 简单 Bug 跳过。

**检索渠道（按优先级自动降级）**：
1. **WebSearch** — 通用搜索，始终可用，首选入口
2. **WebFetch** — 直接抓取特定页面；被墙/403/超时时自动跳过
3. **本地知识库** — `memory/`、CLAUDE.md 中的过往经验
4. **代码库考古** — `git log --grep` / `grep` 搜索历史修复

**关键词公式**：`[异常类型] + [关键报错信息] + [技术栈/框架]`

**降级原则**：WebSearch → 找到链接 → WebFetch 抓取（失败则搜缓存/替代来源）→ 结果不足 → 调整关键词重试（最多 2 轮）→ 仍不足 → 降级本地知识库 + 代码考古 → 标记"无业界参考"

> 完整渠道表、关键词构造、降级流程图、信息甄别标准详见：`reference/research-guide.md`

### 步骤 4：问题定位与根因确认
1. **调用链追溯与现场还原**
   - 从报错日志、堆栈信息（Stacktrace）出发，沿调用链追溯异常发生的直接点与上下文状态。
   - 阅读相关代码，梳理业务逻辑与数据流。
2. **假设提出与验证**
   - 结合调研结果（如有），提出 1~2 个可能的根因假设。
   - 通过推演数据流、分析边界条件、检查调用方契约，判定根因类型：
     - 逻辑错误 / 数据问题 / 配置问题 / 并发问题 / 依赖问题 / 环境问题
3. **定位结论确认**
   - 按标准模板输出定位结论（包含：复杂度等级、报错位置、根因归类、调研参考、修复方向）。
   - **🟢 简单 Bug 可直接给出修复方案，无需等待确认；🟡 中等及以上必须等待用户确认后再进入修复阶段。**
   - 若根因在上游依赖（第三方库/框架），附 workaround 方案或关注链接。

> 输出模板详见：`reference/positioning-template.md`

## 阶段二：修复实施
> ⚠️ **修复编码前必须遵循团队 {代码语言} 安全红线规范**，确保修复代码符合安全基线。
>
> 🔴 **核心原则：全盘考量，不引入新问题。** 修复 Bug 时必须充分理解上下游调用链和关联模块，评估修改对整体系统的影响。任何修复都不能以引入新的 Bug、破坏已有功能或降低系统稳定性为代价。

### 步骤 5：编码修复
1. **最小化改动**：只修改与 Bug 直接相关的代码，严禁"顺手"重构
2. **风格一致**：遵循现有代码风格，保持代码统一性
3. **全盘影响评估（强制）**：
   - 梳理方法/类的所有调用方，确认不破坏已有调用预期
   - 评估共享数据结构、公共方法、全局配置的波及范围
   - 涉及接口契约变更时，同步排查并更新所有调用方
   - 并发场景修复必须验证线程安全，避免引入竞态条件
4. **修复注释**：标注修复的问题、方案选型理由（多方案时）

### 步骤 6：防御性加固（如适用）
若 Bug 暴露了系统性薄弱环节，同步补充防御措施：
- 入参空值 / 边界检查
- 必要的异常捕获与降级
- 脱敏日志增强，便于后续排查

## 阶段三：验证与交付
### 步骤 7：测试验证
> 🔴 **禁止跳过。** 测试深度与 Bug 复杂度匹配。

- **🟢 简单**：原复现步骤不再触发 + 肉眼检查逻辑正确
- **🟡 中等**：↑ + 关联功能正常路径未被破坏 + 1~2 个边界条件
- **🔴 复杂**：↑ + 多种数据组合 + 关联模块回归 + 边界/异常覆盖 + 并发验证（如涉及）+ 评估是否补自动化用例

**测试不通过**：修复但引入回归 → 回退重评方案；原问题未修复 → 回到步骤 2 重新判定根因。

> 完整测试矩阵、用例构造方法、失败处理流程详见：`reference/test-guide.md`

### 步骤 8：自检校验
测试通过后，对照自检清单逐项核验，覆盖修复有效性、代码规范、同步检查三个维度。
> 完整自检清单详见：`reference/self-check-list.md`

### 步骤 9：输出交付物
提供用户选择下列三种任意 1 种或多种交付材料：
1. Bug 修复摘要（精简版结论）
参考文件`reference/delivery/delivery-templates-short.md`
1. ChangeLog 条目（版本日志格式）
输出
```
## [版本号] - YYYY-MM-DD
### Fixed
- [功能名称]: 修复 [问题描述]，根因为 [简述根因]
```
1. 完整任务交付文档（归档用）
参考文件`reference/delivery/delivery-templates-long.md`

> 所有交付模板详见：`reference/delivery/`

### 步骤 10：文档归档
使用 Write 工具将完整交付文档写入 `docs/delivery/` 目录，命名规则：
`{YYYY-MM-DD-HH-mm-ss}-bugfix-{问题简称}.md`
（问题简称用英文小写短横线分隔，如 `null-pointer-on-login`）
