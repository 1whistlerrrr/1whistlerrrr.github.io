# Bug 分级与处置决策 — 详细指南

> 由主 SOP 步骤 2 按需加载。

## 复杂度分级
| 等级 | 特征 | 建议排查深度 |
|:---:|------|------------|
| 🟢 **简单** | 一眼能看出原因（空指针、拼写错误、明显的逻辑疏漏）；改动 ≤ 2 行；影响范围明确且孤立 | **快速路径**：直接给出修复方案，跳过深度调研 |
| 🟡 **中等** | 需要追溯调用链；涉及多个文件；需要理解业务上下文才能判断根因 | **标准流程**：调研 → 定位 → 修复 → 验证 |
| 🔴 **复杂** | 涉及并发/竞态、跨系统交互、数据一致性问题；偶现不易复现；需要改动核心逻辑或接口契约 | **完整流程**：深度调研 → 多方案对比 → 影响评估 → 渐进修复 |

## 处置决策树
在初步判断后，按以下流程决定是否进入修复：

```
可以稳定复现？
├── 是 → 根因是否明确？
│        ├── 是（🟢 简单）→ ✅ 直接进入修复
│        └── 否 → 进入步骤 3 多渠道调研
└── 否 → 影响是否严重（数据丢失 / 安全 / 阻断主流程）？
         ├── 是 → 🔴 优先投入排查，增加日志/监控辅助复现，进入步骤 3
         └── 否 → 评估投入产出比，见下方"不需要修复的场景"
```

## 不需要修复的场景（wont-fix / defer）
以下情况应明确标记，输出判定理由并等待用户确认：

| 场景 | 判定条件 | 处置方式 |
|------|---------|---------|
| **设计意图** | 当前行为是刻意设计，用户误解为 Bug | 补充文档或提示，标记 wont-fix |
| **无法复现 + 低影响** | 偶现且无数据丢失/安全风险 | 加日志/告警，标记为"观察"，定期回顾 |
| **修复成本 >> 影响** | 涉及核心架构重构，但仅影响极少数边缘场景 | 记录 known-issue，排入后续版本 |
| **上游依赖问题** | 根因在第三方库/框架，且无可用 workaround | 关注上游修复进度，评估替代方案 |

> ⚠️ 判定为 wont-fix / defer 时，输出判定理由并等待用户确认，不可擅自关闭。
