# TDD 铁律

以**测试驱动开发**组织编码：先写失败测试，再写最小实现，最后重构。核心循环：红（Red）→ 绿（Green）→ 重构（Refactor）。

## 执行指令

1. **红（Red）** — 为下一个行为写一个**会失败**的测试
2. **绿（Green）** — 写最小代码让它通过（不做多余实现）
3. **重构（Refactor）** — 优化结构，保持测试全绿
4. **重复** — 继续下一个行为，逐步构建功能

### TDD 三条铁律
1. 不写任何生产代码，除非是为了让失败的测试通过
2. 只写刚好能让测试失败的生产代码（不能再多）
3. 只写刚好能修复当前失败的测试的生产代码（不能再多）

## 使用示例

### 用户输入
"用 TDD 实现一个折扣计算函数"

### 预期输出
```text
第1步（红）：写 test_高级会员10%折扣  →  运行失败（函数不存在）
第2步（绿）：写最小实现 `if (tier==='premium') return price*0.9`  →  通过
第3步（红）：写 test_负数价格抛异常     →  运行失败
第4步（绿）：补参数校验 → 通过
第5步（重构）：提取常量/校验逻辑，跑全量测试保持全绿
```

## 故障处理

| 场景 | 应对 |
|------|------|
| 测试写不出就无从下手 | 缩小到最小可测行为，先测一个返回值 |
| 红了很久绿不了 | 检查测试本身是否错了（被测行为理解有误） |
| 重构后测试挂 | 回退最小步，小步重构而非大改 |

## 做什么不做什么

### ✅ 做什么
- 以测试驱动接口与行为设计
- 保证每次改动有测试兜底
- 小步前进，快速反馈，天然防回归
- 与重构配合，安全演进代码

### ❌ 不做什么
- 跳过红阶段直接写实现（违背核心）
- 一次写大段实现（回到传统开发）
- 重构后不跑测试确认
- 把 TDD 教条化强加所有场景（集成/E2E 不适用）
