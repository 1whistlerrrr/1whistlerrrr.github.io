# 测试反模式

评审现有测试，识别**"看起来在测、实际没用"的坏测试**，归类分级并给出改进方案，提升测试代码质量。

## 执行指令

1. **通读用例** — 快速判断每类测试的目的与断言有效性
2. **识别反模式** — 对照常见坏味道逐一排查
3. **归类分级** — 按危害程度：高（假阳性/漏测）/中/低
4. **定位根因** — 是 Mock 滥用、脆弱断言，还是测试设计问题
5. **给出改进** — 具体到用例的重构或删除建议

### 常见反模式清单
- **Mock 滥用**：什么都 Mock，断言的是 Mock 自身而非真实行为
- **脆弱测试**：改一行文案/实现细节就挂
- **碰运气测试**：依赖时间、随机、执行顺序，时过时不过
- **断言缺失**：跑通但没验证结果（无断言或只断真值）
- **测内部实现**：断言私有方法/调用次数，而非对外行为

## 使用示例

### 用户输入
"审查这批 Service 测试质量如何"

### 预期输出
```text
## 反模式识别结果
1. 【高】Mock 滥用 — SaveUser 测试断言的是 mock.repo 被调用，非真实行为
   → 建议：改用内存/真实仓储，断言返回结果与状态
2. 【中】脆弱测试 — 断言了日志文案，改个词就挂
   → 建议：去掉对文案的断言
3. 【低】断言缺失 — 测试跑通但只 expect(1).toBeTruthy()
   → 建议：补真实预期断言
```

## 故障处理

| 场景 | 应对 |
|------|------|
| 反模式泛滥 | 分级排序，先修高危（假阳性/漏测） |
| 测试曾被废弃 | 了解历史原因再决定删除还是重构 |
| 断言有效性难判断 | 问"如果逻辑错了，这个测试能拦得住吗" |

## 做什么不做什么

### ✅ 做什么
- 系统化识别坏测试与反模式
- 评审测试有效性，区分"有效覆盖"与"自欺式覆盖"
- 给出可执行的重构建议
- 建立测试质量基线（不稳定用例数、无效断言数）

### ❌ 不做什么
- 无依据否定他人测试（需有明确反模式证据）
- 只批评不修，不给出改进路径
- 忽略测试废弃的历史原因，一刀切删除
- 把"有测试"当"测试有效"，不深究断言质量
