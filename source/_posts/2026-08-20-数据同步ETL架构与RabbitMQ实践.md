## 摘要

**一句话定位**：数据同步不只有“定时调用接口”一种实现，消息队列也不是默认答案；架构和中间件都应该由数据规模、时效性、可靠性和团队能力共同决定。

**核心价值**：本文先梳理常见的数据同步架构，再提供是否需要消息队列的判断方法，最后比较 RabbitMQ、Kafka、Redis Streams 和云消息服务，并用当前材料安全 ETL 代码说明选型过程。

**适用人群**：负责系统集成、数据中台、ETL、业务解耦或消息中间件选型的开发者和架构师。

---

## 一、不要先问“用哪个消息队列”

### 1.1 先定义要解决的问题

数据同步的目标通常不是单一的“把数据复制过去”，而是下面几类问题的组合：

- 外部系统的数据如何进入中心库。
- 数据格式、编码和主键如何转换。
- 上游和下游速度不一致时，数据放在哪里。
- 网络、数据库或消费者暂时失败时，数据如何恢复。
- 同一份数据是否需要被多个下游使用。
- 同步延迟应该是几秒、几分钟，还是一天。
- 重复消息、乱序消息和半成功任务如何处理。

如果只是“每天凌晨同步一个小表，失败后明天重跑即可”，引入 RabbitMQ 可能增加不必要的运维成本。反过来，如果一个上游接口每小时产生几十万条数据，下游有多个处理者，还要求失败可重试和实时追踪，那么同步直连往往会很快遇到瓶颈。

### 1.2 数据同步的四个维度

| 维度 | 需要确认的问题 |
| --- | --- |
| 数据量 | 单批多少条？峰值多少？增长速度如何？ |
| 时效性 | 允许延迟几秒、几分钟还是几小时？ |
| 可靠性 | 能否丢数据？失败后是否必须自动恢复？ |
| 处理关系 | 一个生产者还是多个？一个消费者还是多个？是否需要重放？ |

架构选择的本质，是在实时性、吞吐量、复杂度、成本和一致性之间做平衡。

## 二、常见的数据同步架构

### 2.1 架构一：同步直连

```text
定时任务 → 调用上游 API → 转换数据 → 写入目标库
```

```csharp
var rows = await sourceApi.GetPageAsync(ct);
var entities = rows.Select(MapToEntity).ToList();
await targetRepository.UpsertAsync(entities, ct);
```

适合数据量小、只有一个消费者、允许整批重跑、且不需要异步削峰的场景。优点是简单、容易调试、事务边界清晰；缺点是上下游强耦合，上游慢会拖住写库，上游失败会直接影响整个任务。

### 2.2 架构二：批处理 ETL

```text
源数据库/API → 临时文件或临时表 → 批量清洗 → 批量写入目标库
```

批处理适合日终汇总、小时级同步和历史迁移。重点是保存时间窗口、页码、批次号、成功数量和失败位置，从而支持断点和补偿。它通常比实时消息架构便宜，但不适合秒级数据更新。

### 2.3 架构三：流水线处理

```text
Extractor → Transform → Validate → Load
```

当抽取、清洗和写库的耗时差异较大时，可以让每个阶段独立限流和扩展。阶段之间可以使用线程池、进程、内存队列或持久化消息队列。流水线的关键是定义每个阶段的失败边界，避免一个慢阶段阻塞全链路。

### 2.4 架构四：消息驱动架构

```text
生产者 → Exchange/Topic → Queue → 消费者 → 目标存储
```

生产者只负责生成消息，消费者负责清洗和写库，中间件负责缓冲、投递、确认、重试和路由。它适合生产速度和消费速度不一致、需要消息级恢复、多个独立消费者或消费者独立扩缩容的场景。

消息驱动不代表天然实时，也不代表自动可靠。持久化、确认、幂等、重试、死信和监控仍需要业务系统自行设计。

### 2.5 架构五：CDC 增量同步

```text
源数据库 WAL/Binlog → CDC Connector → 事件流 → 下游系统
```

CDC 适合源系统主要是数据库、需要捕获新增/修改/删除且不希望频繁全表扫描的场景。Debezium + Kafka 是常见组合。但 CDC 捕获的是数据库变化，不一定包含完整业务语义；表结构变更、删除语义、事务边界和快照都必须单独设计。

### 2.6 架构六：领域事件和工作流

`MaterialReceived`、`MaterialIssued` 这类领域事件表达“业务发生了什么”，不同于复制一行数据库记录。它适合多个业务系统围绕同一业务事实协作，但要求稳定的事件契约和 Outbox 等一致性方案。

跨多个服务的长流程、人工审批和补偿，则更适合 Temporal、Cadence 等工作流引擎，而不是把复杂状态全部塞进 RabbitMQ。

## 三、如何判断是否需要消息队列

### 3.1 五个初筛问题

| 问题 | 如果答案是“是” | 说明 |
| --- | --- | --- |
| 生产者和消费者速度经常不一致？ | 需要缓冲 | 队列削峰填谷 |
| 下游暂时失败时不能丢数据？ | 需要可靠投递 | 需要持久化、确认和重试 |
| 需要多个独立消费者？ | 需要路由/订阅 | Exchange、Topic 或事件流更合适 |
| 消费者需要独立扩容？ | 需要竞争消费 | 队列提供伸缩边界 |
| 需要单条消息重试、死信和重放？ | 需要生命周期管理 | 同步事务通常不够用 |

只有一项为“是”时，不一定需要 RabbitMQ；三项以上为“是”时，应认真评估消息驱动架构。但“数据是否允许丢失”和“是否需要严格同步响应”属于硬约束，不能被平均分掩盖。

### 3.2 一个简单的评分模型

每项按 0～2 分评估：

| 指标 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 峰值流量 | 平稳 | 偶尔突增 | 经常突增 |
| 允许延迟 | 必须同步 | 分钟级 | 秒级异步即可 |
| 失败恢复 | 可人工重跑 | 需要部分重试 | 必须自动重试/死信 |
| 消费者数量 | 1 个 | 2 个 | 多个独立订阅者 |
| 扩展需求 | 基本不扩展 | 偶尔扩展 | 需要横向扩展 |
| 数据价值 | 丢失影响小 | 可补偿 | 绝不能丢失 |
| 团队能力 | 无 MQ 运维经验 | 有基础经验 | 有平台和监控 |

- **0～5 分**：优先同步直连或批处理。
- **6～9 分**：考虑应用内队列、托管队列或轻量消息方案。
- **10 分以上**：消息驱动通常更有价值，但要同时评估运维和一致性成本。

### 3.3 算清楚消息队列的新增成本

引入队列后必须解决：重复消费、消息乱序、消费者失败、队列积压、死信重放、消息版本、Broker 运维、权限和监控。如果这些问题没有答案，消息队列可能只是把同步失败隐藏到队列里。

## 四、需要什么样的消息队列

### 4.1 先区分消息场景

| 场景 | 主要诉求 | 典型技术 |
| --- | --- | --- |
| 任务队列 | 一个任务由一个消费者完成 | RabbitMQ、SQS、Redis Streams |
| 发布订阅 | 一条消息被多个订阅者消费 | RabbitMQ Exchange、Kafka Topic |
| 高吞吐事件流 | 大规模写入、长期保留、重放 | Kafka、Pulsar |
| 延迟任务 | 到期后再执行 | RabbitMQ TTL、云延迟队列、Redis |
| 数据库变更流 | 捕获表变更并传给下游 | Debezium + Kafka/Pulsar |
| 工作流编排 | 多步骤、有状态、可补偿 | Temporal、Cadence |

先确认需要的是任务队列、事件流、延迟队列、CDC 还是工作流，再选产品。

### 4.2 RabbitMQ：业务任务和路由型消息

RabbitMQ 适合：

- 需要 Exchange、Queue、Binding 的灵活路由。
- 需要按业务数据流隔离队列。
- 需要手动 Ack、Nack、重试和死信。
- 消息处理完成后即可确认，不需要长期保存全部历史。
- 单条消息的失败原因和处理状态很重要。
- 消息规模中等，团队已有 RabbitMQ 运维能力。

它的优势是模型直观、路由灵活、确认机制成熟；局限是它不适合承载海量历史事件，也不能当数据库或无限缓存使用。

### 4.3 Kafka：高吞吐、可回放的事件流

Kafka 适合大量事件持续写入、多个消费者各自维护 offset、需要历史重放、CDC、日志采集和数据平台场景。它的核心是 Topic、Partition 和 Consumer Group。

如果只是把材料清洗后写入 PostgreSQL，消息处理完就不再需要，Kafka 的长期保留和分区模型可能是过度设计。

### 4.4 Redis Streams：轻量级流式队列

如果系统已经稳定使用 Redis，且消息规模、可靠性和持久化要求中等，可以考虑 Redis Streams。它支持消费组和 pending entries，开发成本较低，但要评估内存成本、持久化配置和故障恢复能力。Redis 首要职责通常是缓存，不应无条件承担关键消息存储。

### 4.5 云消息服务

云队列适合不希望维护 Broker 的团队，通常提供托管高可用、监控、权限和弹性能力。需要权衡网络延迟、供应商绑定、消息大小/保留期限、本地开发体验和跨云可用性。

## 五、RabbitMQ 继续选什么模型

### 5.1 Exchange 类型

| Exchange | 适用场景 |
| --- | --- |
| Direct | routing key 精确匹配 |
| Topic | 按层级或模式匹配，适合多数据源路由 |
| Fanout | 广播给所有绑定队列 |
| Headers | 按消息头匹配，规则灵活但复杂 |

当前 ETL 使用 Topic 思路，以 `Source` 作为路由键，让不同数据源进入独立队列。若所有消费者都要收到全部消息，Fanout 更合适；若只有一个固定队列，Direct 就足够。

### 5.2 持久化、确认和顺序

重要业务消息通常需要 Durable Exchange、Durable Queue、Persistent Message、Publisher Confirm 和消费成功后的手动 Ack。但这些只能降低丢失风险，不能让 RabbitMQ 和 PostgreSQL 自动组成分布式事务。

RabbitMQ 队列可以提供一定 FIFO 行为，但多个消费者、重试、多个队列和网络恢复都会影响全局顺序。如果同一个聚合对象必须有序，应按业务键固定路由并在数据库中用版本号校验，而不是假设全局天然有序。

### 5.3 延迟重试和死信

```text
主队列 → 失败 → retry 队列（TTL） → 到期 → 主队列
                         ↓
                   超过次数 → DLQ
```

连接超时、数据库瞬断适合指数退避；站点暂时不可用可以延迟重试；404 接口不存在应切换兼容路径或人工处理；字段缺失和格式错误应直接死信。不能对所有错误立即无限 `requeue`。

## 六、当前材料安全 ETL 为什么选择 RabbitMQ

### 6.1 业务约束

当前材料同步具有这些特征：

- 需要访问 5 个数字电站，接口和响应速度不完全一致。
- 材料、仓库、台账、入库和出库是多个独立数据流。
- 库存树递归耗时较长，不能阻塞入库或出库。
- 清洗需要关联项目、材料、组织和人员映射。
- 数据失败后需要按消息重试，而不是整站重跑。
- 目标库需要 Upsert，允许重复投递后安全落库。

这说明系统需要异步边界，但还没有达到必须使用 Kafka 保存海量历史事件的程度，RabbitMQ 与当前需求更匹配。

### 6.2 当前代码链路

```text
CronScheduler
      ↓
MaterialSyncBaseExtractor
      ↓ PushAsync(Source, item)
DataRouter
      ↓ routing key = Source
datacenter.{env}.raw（Topic Exchange）
      ↓
raw.{env}.{Source}（独立队列）
      ↓
SingleSourceProcessor
      ↓ CleanerRegistry.Resolve(Source)
Cleaner → Batcher → PostgresWriter
```

材料同步的 Extractor 包括 `WarehouseExtractor`、`MaterialExtractor`、`MaterialMasterExtractor`、`StockInExtractor`、`StockOutExtractor` 和 `MaterialInventoryExtractor`。入库数据会拆成多个 Source：

```text
api:material
api:material_dict_unit
api:material_stockin_order
api:material_stockin_detail
api:material_inout_archive
```

`Source` 同时承担数据类型标识、RabbitMQ 路由键和 Cleaner 查找键的作用。Extractor 不需要知道目标表，Cleaner 也不需要知道上游接口如何分页。

### 6.3 消费者如何保证处理结果

消费流程是：

```text
收到消息
  ↓
根据 Source 查找 Cleaner
  ↓
Cleaner.CleanAsync
  ├─ 成功 → Batcher / PostgresWriter → BasicAck
  ├─ 瞬时失败 → Retry Queue
  └─ 永久失败 → Dead Letter Queue
```

只有清洗和写库完成后才 Ack。`PostgresWriter` 支持 Insert、Update、Upsert 和 InsertOrIgnore；定时同步依赖业务唯一键和 Upsert 来抵抗重复投递、重试和任务重跑。

### 6.4 这套方案解决过的实际问题

库存树需要递归访问多个组织。如果台账和库存放在同一个 `try` 块中，库存超时会让已经拉取的台账也无法推送。修复后，台账汇总完成即发布到 `api:material_inventory_ledger`，库存使用独立异常边界，保证部分成功。

站点超时还会通过 `CancellationToken` 传播到 Cleaner。取消、网络超时和数据库瞬断应标记为瞬时失败；字段缺失和格式错误才进入永久失败或死信。QfWSC、DwCX 不支持 `GetTreeList` 时，则应按站点切换 `GetList`，不能把 404 无意义地反复重试。

## 七、可靠性边界和监控要求

### 7.1 Ack 不等于数据库事务提交

数据库写入成功但 Ack 失败时，消息可能再次消费；因此要接受“至少一次投递 + 幂等消费”，而不是幻想跨 RabbitMQ 和 PostgreSQL 的全链路原子事务。

### 7.2 队列不能代替任务编排

材料主数据、入库明细和库存台账之间存在业务依赖。独立队列提高隔离性，却不保证不同队列之间的先后顺序。Cleaner 缺少前置数据时，应识别为可重试依赖，必要时增加任务编排、版本号或补偿任务。

### 7.3 必须监控什么

- 队列深度、增长速度和最老消息等待时间。
- 发布成功率、消费成功率和平均/P95 处理耗时。
- 重试次数、死信数量和最后失败原因。
- 各站点、各 Source 的成功/失败数量。
- 数据库连接池、批量写入耗时和失败率。

没有这些指标，就无法判断系统是稳定处理、消费变慢，还是已经陷入重试循环。

## 八、一个可执行的架构选型流程

### 第一步：画出数据生命周期

```text
源 API / 数据库 → 抽取 → 转换 → 校验 → 关联主数据 → 持久化 → 查询/下游事件
```

先确认数据流和失败边界，再画中间件拓扑。

### 第二步：估算吞吐与时效

记录平均/峰值消息数、单条处理耗时、允许积压时长、消息大小和历史保留时间。峰值低且延迟宽松，批处理通常更便宜；高吞吐且需要长期回放，评估 Kafka/Pulsar；单条任务路由、确认和重试更重要，评估 RabbitMQ。

### 第三步：确定投递语义

明确是否接受重复、是否要求顺序、是否需要延迟重试、是否需要死信和人工重放。多数业务系统选择“至少一次投递 + 幂等消费”，这是比 Exactly-Once 更现实的工程方案。

### 第四步：选择消息模型和产品

| 需求 | 优先评估 |
| --- | --- |
| 灵活路由、任务确认、重试、死信 | RabbitMQ |
| 高吞吐、分区、长期保留、重放 | Kafka/Pulsar |
| 已有 Redis、规模较小、轻量消费组 | Redis Streams |
| 不想维护 Broker、运行在云上 | 云队列/事件服务 |
| 捕获数据库变更 | Debezium + Kafka/Pulsar |
| 多步骤业务编排 | Temporal 等工作流引擎 |

## 九、常见误区

### 9.1 “用了 RabbitMQ 就是异步了”

如果发布消息后仍然同步等待消费者结果，系统本质上仍是同步调用，只是中间多了一跳。要明确调用方需要立即响应，还是最终完成通知。

### 9.2 “所有错误都重试”

404、字段缺失和业务校验失败通常重试无效。重试只适用于可能恢复的故障，并且必须有上限、退避和死信。

### 9.3 “消息可靠所以不需要幂等”

消费者崩溃、Ack 丢失和网络恢复都可能造成重复投递。可靠消息系统通常意味着“至少一次”，而不是“绝不重复”。

### 9.4 “Kafka 一定比 RabbitMQ 好”

Kafka 擅长事件流和高吞吐回放，RabbitMQ 擅长业务任务路由和确认。二者解决的问题不同，应该依据消息模型和运维能力选择。

## 十、总结

数据同步架构可以从简单到复杂逐步演进：同步直连、批处理、流水线、消息驱动、CDC 和事件驱动。没有一种架构适合所有场景。

判断是否需要消息队列，关键看生产和消费是否解耦、是否需要削峰、失败是否需要消息级恢复、是否需要多个独立消费者。只有这些需求真实存在时，RabbitMQ 才能带来超过其运维成本的收益。

当前材料安全 ETL 选择 RabbitMQ，是因为它需要将多站点抽取与清洗写库解耦，按 Source 隔离数据流，缓冲上游峰值，支持 Ack、重试和死信，并能通过增加消费者独立扩展处理能力。如果未来需要保存大量历史事件、支持多次回放或承载 CDC 数据流，可以重新评估 Kafka/Pulsar；如果同步量很小且可以整体重跑，就应该坚持简单方案。

好的架构选型不是选择最强的组件，而是用刚好足够的复杂度满足明确的可靠性、吞吐和演进需求。
