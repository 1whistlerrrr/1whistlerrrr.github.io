## 摘要

**一句话定位**：本文解决"面对不同团队规模、业务复杂度和演进压力，如何选出当前条件下最合适的软件架构"这个决策问题。

**核心价值**：读者能获得一套可操作的架构选型思维框架，明白单体 / 模块化单体 / 微服务 / DDD 是不同维度的事物、各自该在什么时机登场，并通过一个真实项目的取舍现场看清"共享库直查"与"暴露服务接口"两种跨模块方式的代价。

**适用人群**：正在做架构选型的技术负责人 / 架构师、从单体走向微服务途中的开发团队、想理解"模块化单体为什么是过渡形态"的一线开发者。

---

## 一、引言

### 1.1 背景

软件系统演进的路上，几乎每个团队都会在某一天被问到："我们要不要上微服务？""是不是该用 DDD 重构了？"面对这些问题，最常见的反应是**追逐业界流行词**：看到大厂都在拆微服务就跟着拆，听说 DDD 很"高级"就强行落地。结果往往是——微服务拆到一半被分布式事务和链路追踪拖垮，DDD 画了一堆漂亮的限界上下文图却落不进代码。

真实世界的残酷之处在于：**架构没有银弹，只有"在当前约束下最合适"的形态。** 而我最近参与的一个系统，恰好把这场选型拉扯完整地演了一遍。

### 1.2 动机

选错架构的代价是巨大的：过度设计的微服务带来常年运维负债，毫无边界的单体让协作逐渐失控。而更隐蔽的问题是——**很多人根本分不清自己在比较什么**。把"单体"和"微服务"放在一起比还能理解，但把"DDD"也塞进来就乱了：DDD 不是一种物理架构，它和"拆不拆服务"根本不在同一个维度上。不先把概念厘清，任何选型讨论都是空中楼阁。

### 1.3 目标

- 厘清单体、模块化单体、微服务、DDD 四个概念的本质区别与联系；
- 用一个真实项目的架构决策现场，说明"共享数据库直查表"与"暴露服务接口"两种跨模块方式各自的代价；
- 给出一套**按约束条件（团队、复杂度、流量、演进风险）选型**的决策框架；
- 诚实地说清楚：DDD 什么时候才是真正该登场的工具。

## 二、核心概念

### 2.1 概念定义

四个概念分属两个维度，不该混为一谈：

| 概念 | 回答的问题 | 本质维度 |
|---|---|---|
| **单体 Monolith** | 代码怎么组织、部署几个进程 | 物理形态 |
| **模块化单体 Modular Monolith** | 代码边界怎么画、怎么隔离 | 物理形态 + 逻辑边界 |
| **微服务 Microservices** | 拆成几个独立部署的服务 | 物理形态 |
| **DDD 领域驱动设计** | 业务边界（限界上下文）画在哪 | 建模方法论 |

一句话概括彼此关系：**DDD 管"边界画在哪"，单体 / 微服务管"边界怎么落地"**。它们是互补关系，不是竞争关系。

### 2.2 技术原理

模块化单体是理解全部问题的钥匙。它的形态是：

- **一个进程、一个统一 DI 容器、一个共享数据库**；
- 但代码按业务领域切成**多个独立模块项目**，模块之间不互相引用对方 API；
- 每个模块只依赖**共享数据契约层**（实体 + DbContext + QueryService）和**共享基础设施层**。

跨模块数据访问在这个形态下有两条通道：

1. **共享 `AppDbContext` 直接 EF 查对方表**——因为所有模块共用一个数据库，表都在同一个进程里，想查就查：
   ```csharp
   // 模块 A 直接查模块 B 的表，不需要经过 B 的任何服务
   public class HazardousOverviewRepository(AppDbContext dbContext) {
       public async Task<int> CountAsync(long projectId)
           => await dbContext.SomeEntity.Where(x => x.ProjectId == projectId).CountAsync();
   }
   ```
2. **共享 DAL 里的 QueryService（接口）**——接口和实现都在共享契约层，由所属模块注册进统一容器，其他模块只注入接口，运行时由容器解析。

### 2.3 架构设计

| 特性 | 传统单体 | **模块化单体（推荐过渡态）** | 微服务 |
|---|---|---|---|
| 代码组织 | 一个大项目 | 多模块独立项目 | 多个独立服务 |
| 进程 | 1 | 1 | 多个 |
| 数据库 | 1 | 1（共享） | 每服务独立 |
| 跨模块访问 | 直接调 | 共享库直查 + 共享服务接口 | 只能 HTTP/RPC/消息 |
| 隔离强度 | 无 | 编译期（程序集）隔离 | 全隔离（进程 + 库） |
| 复杂度 | 最低 | 中 | 高（分布式事务、发现、监控） |
| 演进路径 | 重构成本高 | **可平滑演进为微服务** | 终极形态 |

模块化单体最大的价值在于：**它拿到了微服务的大部分"代码隔离"好处，却保留了单体的简单性（一个库、一个进程），并且保留了通向微服务的平滑路径——将来某模块流量真爆了，把它拎出去单独部署即可。**

## 三、实践指南

> 这是一篇架构思考类文章，本节把"环境准备 / 步骤"改造成"选型前的准备 / 决策流程"，其中会穿插真实代码形态作为判断依据。

### 3.1 决策前的准备

选型不是拍脑袋，先确认三件事：

1. **团队规模**：实际参与长期维护的人有几个？
2. **业务边界**：能不能画出稳定的领域边界？画出几条？
3. **数据访问现状**：现在的模块之间是共享一个库直查表，还是已经通过服务接口调用了？

### 3.2 决策流程（步骤说明）

1. **先画边界，再定形态**。用 DDD 的限界上下文思路（哪怕不做严格 DDD）把业务切成模块——现场管理、劳务实名制、机械设备、危大工程，天然对齐领域，每个模块就是一块自洽的地盘。
2. **默认选模块化单体**。除非有明确理由，否则不要直接上微服务。模块化单体是几乎所有团队的默认甜点区。
3. **只拆"会爆的那个"**。当某个模块流量或团队规模单独突破阈值时，只把那个模块拆出去，而不是全拆。
4. **保持"自包含 + 共享契约"**。跨模块读数据优先走共享库直查或共享 DAL 接口；只有"想让别人复用的复杂逻辑"才定义接口并注册，接口放共享契约层，不引用对方模块 API。

### 3.3 代码层面的判断标准

判断"某段跨模块访问该用哪种方式"，用一条标准：

> **别人是想"查你的数据"，还是想"调用你的逻辑"？**
> 查数据 → 共享 DAL 直查表；复用逻辑 → 定义接口 + 注册服务。

```csharp
// ❌ 反面：为了复用，直接引用对方模块 API（硬程序集依赖）
// var result = await laborModule.PersonManagementService.BuildFilterQuery(...);

// ✅ 正面：只引用共享 DAL，自包含查表
public class WorkerStatsRepository(AppDbContext dbContext) {
    public async Task<int> CountAsync(long projectId)
        => await dbContext.Workers.CountAsync(w => w.ProjectId == projectId);
}
```

### 3.4 常见问题

- **"要不要把所有方法都注册成服务，方便以后拆库时给别人调？"** → 不用。按需暴露，别提前白写一堆没人调的接口。等真拆微服务、物理上不能直查表时，再按需改写成服务接口。
- **"模块 A 直接查模块 B 的表，是不是破坏了 DDD？"** → 在共享库单体里这是务实且常见的妥协，纯 DDD 确实禁止"上下文穿透"，但那是拆微服务那天才需要用纪律收尾的事。
- **"微服务是不是更先进？"** → 更分散不等于更先进。没有分布式事务、链路追踪、多服务部署的运维能力，微服务是灾难而非资产。

## 四、案例分析

### 4.1 案例背景

我参与的一个系统采用模块化单体：一个进程、一个容器、一个数据库，按业务切成 SiteManagement（现场）、LaborRealNameSystem（劳务）、MechanicalEquipment（机械）、ProjectDashboard（项目总览大屏）等独立模块。模块之间不互相引用 API，只依赖共享数据契约层。

### 4.2 解决方案

新需求要在 ProjectDashboard 模块里实现"建筑工人统计 + 设备统计"。此时出现了两条路线：

- **路线 A（嵌入源模块）**：把统计逻辑塞进 SiteManagement / Labor 等源模块，甚至让 ProjectDashboard 直接 `ProjectReference` 另外三个模块的 API，调用对方注册的服务，返回对方的 ViewModel。优点：代码最少、口径天然对齐。
- **路线 B（自包含 + 共享契约）**：统计逻辑自己在 ProjectDashboard 内用共享 `AppDbContext` 写 EF 查询；工区在线推导这类复杂逻辑定义成**接口**放在共享契约层，先注册一个空实现（在线数暂显 0），由其他团队后续提供真实现接管；只有"下钻要返回对方模块的标准 ViewModel"这一处绕不开的耦合，才最小化引用对方模块。

最终选择 **路线 B**。原因正是本文反复强调的架构判断：路线 A 让 ProjectDashboard 与三个模块建立硬程序集依赖，**既破坏了为将来拆微服务准备的程序集隔离，又绕过了共享契约层**——表结构一改，所有直连的模块一起崩。

### 4.3 效果评估

- **短期**：路线 B 的统计逻辑自包含、可独立编译调试，源模块零改动、零新增依赖；工区在线通过"接口 + 空实现"解耦，其他团队可并行实现，不阻塞主流程。
- **长期**：模块边界保持干净，未来拆微服务时，统计逻辑不产生跨模块硬依赖；唯一的耦合点（下钻 ViewModel）被收敛到最小范围，是可管理的。

## 五、最佳实践

### 5.1 技巧与建议

- **用五问法做选型**：① 未来 6~12 个月复杂度会怎么变？② 业务边界稳定吗？③ 团队几人维护？④ 单点在哪，会不会爆流量？⑤ 现在的隔离让"将来想拆时拆得动"吗？
- **YAGNI 优先**：别为一年后可能不存在的复杂度付今天的钱。
- **默认模块化单体，只拆该拆的**：拆微服务是手段，不是目标。

### 5.2 演进优化

- 先做到**程序集隔离**（模块互不引用 API），这是成本最低、收益最大的一步。
- 当真正需要拆某模块时，再把"共享库直查表"改写成"调用对方暴露的服务接口"，并把被跨模块访问的数据收敛成契约。

### 5.3 安全与治理考虑

- 跨模块直查表时，遵守**只读**原则，不跨模块写库，写操作留在数据所属模块内，避免一致性失控。
- 接口一旦对外暴露，就是长期契约：**保证接口稳定，表结构可以随意内部改**——这正是"暴露服务"相比"直查表"的核心收益。

## 六、总结与展望

### 6.1 核心要点回顾

1. 单体 / 模块化单体 / 微服务是**物理形态**，DDD 是**建模方法**，维度不同，不该混比。
2. 架构选型没有最优，只有**在当前约束（团队 / 复杂度 / 流量 / 演进风险）下最合适**。
3. 模块化单体是多数团队的正确默认选择：拿到隔离收益、保留单体的简单、留好拆分路径。
4. 共享库直查表 vs 暴露服务接口，是"现在最简单"和"将来可拆"之间的取舍，按需切换，别提前付费。
5. 很多"模块化单体"并不是严格 DDD——这不丢人，是务实妥协；等拆微服务那天，才必须用 DDD 的纪律收尾。

### 6.2 未来发展方向

模块化单体与微服务之间不是非此即彼，而是一条**连续谱**：今天的模块边界，就是明天的服务边界。当某个模块的流量、数据规模或团队自治需求真正突破临界点时，把它平滑拆成独立服务；而 DDD 提供的那套"限界上下文独占数据、对外只暴露接口、加防损坏层、必要时领域事件"的纪律，正是你跨过那道门槛时要用的工具箱。**架构不是设计出来的终点，而是不断演进、每步都留好后路的过程。**
