## 摘要

**一句话定位**：本文以材料安全数据同步业务为例，介绍如何设计一条可隔离、可恢复、可观测的 ETL 链路。

**核心价值**：读者可以理解材料台账、入库、出库和库存数据之间的关系，并掌握处理站点超时、接口不兼容、取消异常和部分失败的实用方法。

**适用人群**：负责企业系统集成、数据中台、ETL 任务或分布式后台服务的开发者与运维人员。

---

## 一、引言

### 1.1 背景

在材料安全管理场景中，数据通常分散在多个电站或项目系统中。上游系统负责记录材料台账、入库单、出库单以及库存树；中心平台则需要定期拉取这些数据，完成清洗、关联和入库，为项目总览、库存统计和安全管理提供统一数据源。

这类任务表面上是“定时调用几个接口”，实际上是一条跨网络、跨数据库、跨消息队列的长链路：

```text
电站 API
   ↓
抽取器 Extractor
   ↓
消息队列 / PushAsync
   ↓
清洗器 Cleaner
   ↓
中心数据库
   ↓
业务查询与统计
```

链路中的任何一个环节变慢，都可能表现为数据缺失、任务卡住或大量误报。因此，数据同步的重点不只是“能不能拉到数据”，还包括失败时是否能保住已经成功的数据，以及下一次任务能否安全恢复。

### 1.2 动机

一次实际排障中，系统先后暴露出多个典型问题：站点超时触发数千条“清洗失败”日志；库存树拉取超时导致已经获取的 681 条台账数据没有推送；部分站点返回 404，但其他站点接口正常；测试任务运行很久却没有任何进度输出。

这些问题说明，ETL 系统的可靠性不是由某个单独组件决定的，而是由超时边界、资源隔离、异常分类、数据提交时机和可观测性共同决定的。

### 1.3 目标

本文希望完成三件事：

1. 从业务角度解释材料安全数据同步为什么要拆分不同数据流。
2. 从技术角度总结 ETL 链路中的超时、取消、接口差异和资源共享问题。
3. 提炼一套可以迁移到其他数据同步项目中的故障治理方法。

## 二、核心概念

### 2.1 材料安全数据的业务模型

材料同步通常包含四类数据：

| 数据类型 | 业务含义 | 典型特点 |
| --- | --- | --- |
| 材料台账 | 某个站点当前管理的材料主数据 | 适合作为材料基础信息来源 |
| 入库数据 | 材料进入仓库或项目现场的记录 | 可能需要递归获取材料树 |
| 出库数据 | 材料从仓库领用或发出的记录 | 结构相对简单、时效性较高 |
| 库存数据 | 当前库存数量、仓位和层级关系 | 接口可能存在树形与平铺两种实现 |

台账是“材料是什么”，入库和出库是“材料如何流动”，库存是“材料现在在哪里、还剩多少”。这几类数据既有关联，又有不同的性能特征和失败模式，因此不适合强行放在一个不可分割的处理单元中。

### 2.2 ETL 的三个阶段

- **Extract（抽取）**：按站点、接口和分页规则从上游系统获取原始数据。
- **Transform（清洗）**：统一字段、补齐外键、关联材料字典，并处理脏数据和缺失数据。
- **Load（写入）**：将处理后的消息写入中心数据库或下游业务存储。

在异步系统中，三个阶段往往通过消息队列解耦。这样可以提高吞吐量，但也引入了消息重试、取消令牌传播、消费者恢复和最终一致性等问题。

### 2.3 按站点设置超时预算

数据同步的超时不应只设置在单个 HTTP 请求上，还应覆盖一个站点从获取、推送、清洗到写入的完整过程。可以把它视为一个站点级预算：

```csharp
using var stationCts = CancellationTokenSource.CreateLinkedTokenSource(globalToken);
stationCts.CancelAfter(TimeSpan.FromMinutes(15));

await ExtractAsync(station, stationCts.Token);
await PushAsync(station, stationCts.Token);
```

站点级预算可以防止单个异常站点长期占用任务资源，但必须与数据流隔离结合使用，否则一个阶段超时仍可能回滚或丢弃其他阶段已经完成的数据。

## 三、实践指南

### 3.1 抽取器的职责拆分

原先的 `InoutOrderExtractor` 同时处理入库和出库。由于入库需要递归拉取材料树，处理时间明显更长，入库超时会连带阻塞出库。

更合理的设计是拆分为两个抽取器：

- `StockInExtractor`：负责入库数据和必要的材料树、字典构建。
- `StockOutExtractor`：负责出库数据，不承担材料树的耗时任务。

两个抽取器共享站点遍历、超时管理和通用请求能力，但各自拥有独立的调度和失败边界。这样既符合单一职责原则，也能让出库这种相对简单的数据流及时完成。

### 3.2 让已完成的数据尽快落地

一个常见错误是把台账和库存放在同一个 `try` 块中：先获取台账，再获取库存，最后统一 `PushAsync`。当库存树耗时超过站点预算时，外层异常会让台账也无法推送。

更稳妥的策略是“先提交已完成数据，再处理高风险数据”：

```csharp
// 台账已经汇总完成，立即推送
await PushAsync("api:material_inventory_ledger", ledgerMessages, stationToken);

// 库存是独立数据流，失败不影响台账
try
{
    var inventory = await FetchInventoryAsync(station, stationToken);
    await PushAsync("api:material_inventory", inventory, stationToken);
}
catch (OperationCanceledException) when (stationToken.IsCancellationRequested)
{
    logger.LogWarning("{Code} 库存拉取超时，台账已保留", station.Code);
}
```

这里的关键不是简单地增加 `try-catch`，而是重新定义“一个任务是否成功”：台账成功、库存失败时，系统应该记录部分成功并允许下次补偿，而不是把整个站点标记为全量失败。

### 3.3 正确处理取消异常

站点超时触发后，取消令牌会继续向下游传播。如果清洗器仍把取消异常当作普通业务异常，就会产生大量误导性的“清洗失败”日志。

建议按异常性质分类：

```csharp
try
{
    var row = await repository.FirstOrDefaultAsync(query, token);
    await SaveAsync(row, token);
}
catch (OperationCanceledException) when (token.IsCancellationRequested)
{
    // 瞬时失败：记录为可重试，不要伪装成永久数据错误
    await MarkTransientAsync("station-timeout");
}
catch (FormatException ex)
{
    // 永久失败：保留原始数据和字段信息，进入人工处理或死信队列
    logger.LogError(ex, "数据格式错误");
}
```

取消异常至少要区分两种情况：任务主动超时，以及调用方主动终止。两者都不应直接归类为数据质量问题，但都需要在指标中体现，以便判断重试是否有效。

### 3.4 兼容不同站点的接口版本

不能假设所有站点部署了完全一致的 API。实际排查发现，QfWSC 和 DwCX 没有部署 `GetTreeList`，请求该接口会返回 404；它们只提供 `GetList` 平铺分页接口，而其他站点支持树形接口。

因此，接口适配应显式建模，而不是遇到 404 后无限重试：

```csharp
var useFlatList = station.Provider is TokenProvider.QfWSC or TokenProvider.DwCX;

var rows = useFlatList
    ? await FetchPagedAsync<MaterialDto>(station, "/Material2Stock/GetList", token)
    : await FetchWarehouseTreeAsync(station, token);
```

404 通常意味着“接口不存在或版本不支持”，而不是网络抖动。对这类错误，应该切换兼容路径、降级能力或记录站点能力矩阵，而不是增加重试次数。

### 3.5 建立实时进度日志

长时间同步任务必须让操作者知道“正在处理什么、已经处理多少、是否仍在前进”。建议日志至少包含站点、接口、分页范围、累计数量、阶段和耗时：

```text
拉取 Inventory（YyCX）第 401-500 条 / 共 681，累计 681
电站 YyCX 入库同步完成：材料 120 / 单 42 / 明细 681 / 归档 0
材料库存树（YyCX, org=3）父节点 18 处理完成，叶节点累计 934
```

测试环境也应使用接近生产的日志配置。文件日志需要实时刷新，并允许其他进程读取：

```bash
SYNC_EXTRACTORS=Inventory dotnet test DatacenterAPP.Tests \
  --filter "FullyQualifiedName~SyncViaExtractorsAndCleaners_ToDevDb"

tail -f /tmp/material-sync.log
```

如果只有测试结束后才输出日志，开发者就无法判断任务究竟是慢、卡住、等待重试，还是已经失败。

## 四、案例分析

### 4.1 案例一：8 分钟超时产生 3486 条清洗失败

测试中出现 3486 条 `清洗失败: The operation was canceled.`。排查调用链后发现，站点级 8 分钟预算在 `PushAsync` 阶段耗尽，后续消息到达清洗器时携带的令牌已经取消，数据库查询立即抛出 `OperationCanceledException`。

这不是 3486 条脏数据，而是一次站点级超时被下游逐条放大记录。处理方式包括：

1. 根据真实数据量将预算从 8 分钟调整为 15 分钟。
2. 清洗器识别取消异常，标记为瞬时、可重试失败。
3. 在错误聚合时按站点和批次归并，避免逐条制造噪声。

### 4.2 案例二：库存超时导致 681 条台账丢失

YyCX 站点需要按多个组织递归读取库存树，库存阶段耗时超过预算。由于台账和库存共用一个 `try` 块，台账虽然已经读取了 681 条，但在最终统一推送前发生超时，最终表现为台账推送 0 条。

修复后，台账汇总完成即推送，库存独立执行。即使库存继续超时，台账仍然可以保留，下一轮任务再补偿库存。这体现了同步系统中的一个重要原则：**成功的数据不应等待高风险阶段完成后才提交**。

### 4.3 案例三：所有站点统一返回 502

排查清丰站点时，进一步测试了 5 个站点，发现它们都在约 5 秒后返回空响应体的 HTTP 502。公网访问正常，内部服务正常，响应头中的 `Proxy-Connection` 也表明请求经过网关或 WAF。

当多个站点返回相同状态码、相同耗时和相似响应特征时，问题更可能位于共享网关、路由或上游平台，而不是某一个站点数据库。此时应停止针对单站点反复重试，转而检查平台整体可用性，并在 ETL 中增加站点健康检查和自动跳过机制。

### 4.4 效果评估

这组治理措施带来的收益并不只体现在“任务成功率”上：

| 问题 | 治理前 | 治理后 |
| --- | --- | --- |
| 单站点超时 | 可能拖累整个流程 | 限制在站点和数据流边界内 |
| 取消异常 | 被记录为大量清洗失败 | 标记为瞬时、可重试事件 |
| 库存阶段失败 | 已获取台账可能丢失 | 台账先落地，库存独立补偿 |
| 接口版本差异 | 404 后重复重试 | 按站点能力选择兼容接口 |
| 长任务运行 | 无法判断进度 | 可按站点、分页和阶段观察 |

## 五、最佳实践

### 5.1 资源隔离

数据库连接池、RabbitMQ 连接和通道属于共享资源。一个慢查询或异常消费者可能阻塞其他模块。长期优化方向包括按模块或优先级隔离连接池、使用多通道和多连接，并为消费者恢复设计重平衡机制。

### 5.2 错误分类与重试策略

建议至少区分以下错误：

- 网络抖动、网关超时、站点暂时不可用：可重试或跳过后补偿。
- 取消令牌触发：记录为瞬时失败，不标记为脏数据。
- 404 接口不存在：切换兼容实现或更新能力配置，不做盲目重试。
- 字段缺失、格式错误、主数据无法关联：进入死信或人工处理流程。

### 5.3 可观测性设计

日志之外，还应记录每个站点的请求耗时、处理数量、成功数量、失败数量、重试次数和最后成功时间。健康检查可以在正式同步前快速识别不可用站点，避免把整个超时预算消耗在无效请求上。

### 5.4 性能优化

库存树递归是主要耗时来源，可以从以下方向优化：

1. 缓存不会频繁变化的组织和材料字典。
2. 对父节点请求设置并发上限，避免无限并发压垮上游。
3. 支持增量同步，减少重复遍历整棵库存树。
4. 为台账、入库、出库和库存分别设置批次大小与超时预算。

### 5.5 安全考虑

站点 API 的令牌获取应有独立信号量和登录超时，避免多个任务同时刷新令牌。日志中不要输出完整令牌、密码或连接字符串；站点地址、组织编号等诊断信息也应根据环境进行脱敏。

## 六、总结与展望

### 6.1 核心要点回顾

材料安全数据同步的可靠性，最终取决于几个边界是否清晰：

1. 抽取器按业务数据流拆分，避免一个慢阶段阻塞其他阶段。
2. 超时预算按站点和任务设置，并覆盖完整处理链路。
3. 已完成的数据尽快推送，部分失败要能保留成功结果。
4. 取消、网络、接口版本和数据质量错误要分类处理。
5. 用结构化实时日志和指标观察长任务，而不是依赖任务结束后的单一结果。

### 6.2 未来发展方向

下一步可以建设站点能力矩阵和健康检查中心，统一管理不同版本站点支持的接口；同时引入同步任务看板，展示实时进度、历史延迟和失败分布。对于高价值数据，还可以增加幂等键、断点续传和补偿任务，使同步从“定时全量尝试”逐步演进为“可恢复的数据管道”。
