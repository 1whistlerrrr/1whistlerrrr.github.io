## 摘要

**一句话定位**：本文记录一个真实生产接口的性能治理过程——一个返回 8 个统计指标的"建筑工人统计卡"接口，实际要查 13 次数据库、其中入场判定一个指标就占 6 次往返（还拖着 4 张表全表拉到内存），最终用一条相关 EXISTS 查询把它压到 1 次。

**核心价值**：从"接口为什么慢"的拆解方法，到 EF Core 里 `AsEnumerable` 客户端求值的隐蔽陷阱，再到"语义等价"地改写查询，最后给出可复用的性能治理清单。

**适用人群**：写后端接口、用 EF Core / 类 ORM 的开发者；被"接口慢"反复折磨的排查者。

---

## 一、引言

### 1.1 背景

业务方反馈：单项目大屏上"建筑工人"统计接口很慢。这个接口要一次性返回 8 个数字：总人数、特种作业工、一般工、在线、在册（绑定头盔）、超龄、证书不符合、入场资料缺失。每一个数字背后都是一次（或多次）数据库查询。

性能优化的第一步永远是**先量化**：这个接口到底查了多少次数据库？慢在哪一步？而不是凭感觉改。

### 1.2 动机

"接口慢"是个症状。如果没有精确拆解，常见的做法是乱加缓存、乱加索引、或把所有查询硬塞进一条 SQL——结果要么没效果，要么把数字改错了。本文的价值在于展示一套**可复现的拆解 → 定位 → 改写 → 验证**的方法，尤其强调改查询时要保证**口径不变**。

### 1.3 目标

- 说清楚"一次接口调用"背后真实的数据库往返结构；
- 暴露 EF Core 里一个隐蔽的性能陷阱（`AsEnumerable` 把整表拉到客户端）；
- 给出把"入场判定"从 6 次往返压到 1 次的改写，并证明它和原逻辑语义等价；
- 总结通用的性能治理套路。

## 二、核心概念

### 2.1 概念定义

- **数据库往返（round trip）**：应用和数据库之间一次完整的"发 SQL → 等结果"过程。一次接口调用里往返次数越多，网络延迟和连接占用越重。
- **连表查询**：把本来分多次查的数据，通过 JOIN / 子查询 / EXISTS 合并成一次查询。
- **相关子查询 / EXISTS**：子查询里引用了外层查询的列。`WHERE EXISTS (SELECT 1 FROM ... WHERE ... = 外层.id)` 常用于"判断某条记录是否存在"。
- **客户端求值（client-side evaluation）**：本应在数据库里完成的过滤，却把数据搬回应用内存里做。这是 ORM 里最常见的性能坑。

### 2.2 技术原理

**EF Core 的翻译与物化**。EF Core 会尽力把 LINQ 翻译成 SQL。但当一个表达式无法翻译（比如用了反射取属性），很多开发者会写 `.AsEnumerable()` 强制"先把整张表查回来，再在内存里过滤"。这在功能上没错，代价是**全表传输 + 内存过滤**，数据量一大就崩。

**`Any()` → `EXISTS`**。EF Core 把 `集合.Any(x => 条件)` 翻译成相关子查询 `EXISTS (...)`。`EXISTS` 只关心"有没有"，命中的第一行就停，比 `SELECT ... WHERE person_id IN (...)` 再 `.Distinct()` 更适合"判存在"。

**B-tree 复合索引的最左前缀**。索引 `(a, b)` 只能高效匹配从 `a` 开头的条件；只按 `b` 查时用不上。所以"按人查材料"需要 `person_id` 开头的索引。

### 2.3 架构设计：先算出一批 id，下游全部复用

这个接口的关键结构是：**第一步先把"这个项目在场的建筑工人"算出来（记作 `workerIds`），之后 8 个指标全部拿这批 id 去各自的表里问"这批人里谁命中"**。这也意味着：下游任何一步都不需要重新判断"是不是在场的建筑工人"——那些重复判断，就是优化空间。

## 三、实践指南

### 3.1 环境准备

- .NET 8 / C# 12
- EF Core + Npgsql（PostgreSQL）
- 测试库（用于逐字段比对 + Npgsql SQL 翻译测试）

### 3.2 代码实现：入场判定的改写

**优化前**：入场判定 = 查一次人员状态 + 5 张材料表逐表各查一次。

```csharp
// 优化前：6 次数据库往返
private async Task<HashSet<long>> ResolveEntryUnqualifiedIdsAsync(long projectId, List<long> personIds) {
    // ① 重复查 project_vs_person 拿状态（第一步其实已经算过这批人是在场的了）
    var statusMap = await personQueryHelper.BuildPersonStatusMapAsync(projectId, personIds);
    // ② 内部对 5 张材料表逐表查询（其中 4 张整表拉到内存再反射过滤）
    return await personQueryHelper.GetEntryUnqualifiedPersonIdsAsync(statusMap);
}
```

**优化后**：一条相关 EXISTS 查询，把 5 张材料表的"有没有"一次性问完。

```csharp
// 优化后：1 次数据库往返
private async Task<HashSet<long>> ResolveEntryUnqualifiedIdsAsync(List<long> personIds, CancellationToken ct) {
    var idSet = personIds.ToHashSet();
    if (idSet.Count == 0) return [];

    return (await BuildEntryMaterialQuery(dbContext, idSet).ToListAsync(ct))
        .Where(r => !(r.HasContract && r.HasSkillCert && r.HasEntryMedical
                      && r.HasHealthNotice && r.HasEntryEducation))
        .Select(r => r.Id)
        .ToHashSet();
}

internal IQueryable<EntryMaterialRow> BuildEntryMaterialQuery(AppDbContext ctx, IReadOnlyCollection<long> personIds) {
    var idSet = personIds.ToHashSet();
    return ctx.Persons
        .Where(p => idSet.Contains(p.Id))
        .Select(p => new EntryMaterialRow(
            p.Id,
            ctx.PersonContracts.Any(c => c.PersonId == p.Id),            // EXISTS person_contracts
            ctx.PersonVsCertifications.Any(c => c.PersonId == p.Id),     // EXISTS person_vs_certifications
            ctx.PersonHealthRecords.Any(r => r.PersonId == p.Id && r.ExaminationType == ExaminationType.Entry),
            ctx.PersonAdditionalMaterials.Any(m => m.PersonId == p.Id && m.MaterialType == AdditionalMaterialType.HealthDeclaration),
            ctx.TrainingPersonDetails.Any(t => t.PersonId == p.Id)));    // EXISTS training_person_details
}
```

生成的 SQL 大致是：

```sql
SELECT p.id, p.person_type,
       EXISTS (SELECT 1 FROM person_contracts WHERE person_id = p.id),
       EXISTS (SELECT 1 FROM person_vs_certifications WHERE person_id = p.id),
       -- ... 其余三张材料表同理
FROM person p
WHERE p.id = ANY ($1)
```

### 3.3 步骤说明

1. **列清单**：把接口调用的每一条 SQL 拉出来，数清楚往返次数。不是"5 次"而是"13 次"。
2. **找大头**：入场判定一个指标占 6 次串行往返，且 4 张表是整表拉到内存——这就是主瓶颈。
3. **去重复**：入场判定里"查人员状态"那趟，和第一步"算 workerIds"查的是同一张表同一批人，纯重复，删。
4. **合查询**：5 张材料表的"有没有"，用相关 EXISTS 一次问完。
5. **证等价**：候选集在第一步已保证全在"在场"状态，所以"在场且五类材料不齐" = "五类材料不全的人"，与原有口径严格一致。
6. **留测试**：把新查询暴露成 internal 方法，写 Npgsql SQL 翻译断言，防止以后被改回逐表查。

### 3.4 常见问题

| 问题 | 说明 |
|---|---|
| 明明写了 `Where`，为什么还慢？ | 很可能 `.AsEnumerable()` 把过滤挪到内存了——检查有没有"整表拉回"的痕迹 |
| 并行查几张小表是不是更好？ | 并行减少的是**墙钟耗时**，不是**往返次数**，还占用更多连接；先合并查询，再考虑并行 |
| 改了查询，数字会不会变？ | 必须做"语义等价"论证 + 用测试库逐字段比对，任何口径变化都要显式确认 |
| EF 并发报"context 上已有操作进行"？ | EF 同一 DbContext 禁止并发查询，并行时必须各用独立上下文 |

## 四、案例分析

### 4.1 案例背景

单项目大屏"建筑工人统计卡"接口（`ProjectDashboardWorkerRepository.GetWorkerStatsAsync`），一次调用返回 8 个指标，每个指标都依赖不同的表：人员表、进场表、头盔表、证书表、体检表、培训表、附加材料表……

### 4.2 解决方案

**第一步：逐段拆解往返**。把接口的查询按顺序列出来：

| # | 查询内容 | 往返 |
|---|---|---|
| 1 | 已进场建筑工人（persons JOIN project_vs_person） | 1 |
| 2 | 组织范围过滤（递归 CTE） | 1 |
| 3 | 在册（helmet_vs_person） | 1 |
| 4 | 超龄 | 1 |
| 5 | 证书不符合 | 1 |
| 6~8 | 工区在线 | 2~3 |
| 9 | **入场 = 重复查 project_vs_person 状态** | 1 |
| 10~14 | **入场材料：5 张表逐表各查** | 5 |

总计约 **13 次往返**。其中入场判定一个指标就占 6 次，且 4 张材料表是整表拉到内存再过滤——**这就是"接口慢"的真凶**，而不是别的。

**第二步：改写入场判定**。利用"workerIds 已全在场"这一事实，把"查状态 + 5 张表"压成一条相关 EXISTS 查询（见 3.2）。`Any()` 翻译成 `EXISTS`，只判"有没有"，不再逐表全表拉取。

### 4.3 效果评估

- 入场判定：**6 次往返 → 1 次**；且不再把 4 张材料表整表搬进内存。
- 接口总往返：约 13 次 → 约 8 次，去掉了最重的串行瓶颈。
- 正确性：通过语义等价论证 + 测试库比对，8 个指标数值与优化前一致。
- 验证：348 个测试全部通过（含新增的 Npgsql SQL 翻译断言，锁定"单条查询 + EXISTS 子查询"这个形态，防止回退）。

> 性能数据本身不是重点，重点是**这一改动是"零风险、纯收益"的**：查询次数变少、传输量变小、语义不变。

## 五、最佳实践

### 5.1 技巧与建议

- **先数往返，再谈优化**：接口慢先把它调用的 SQL 全列出来，按往返次数和单条耗时排序，抓最大的。
- **把"判存在"和"取数据"分开**：只需确认"有没有"的，用 `Any()`/`EXISTS`，别把整表或整行搬回来。
- **警惕客户端求值**：`.AsEnumerable()` 是整表拉回的信号，凡是能翻译成 SQL 的过滤都别用。
- **主动留测试**：把关键查询暴露成 internal，写 SQL 翻译断言，性能优化不回归。

### 5.2 性能优化：通用套路

1. **减往返**：合并查询、去重、能一次查完的不分多次。
2. **用连表/子查询**：异构表不能 UNION，但可以用相关 EXISTS 一次问完"多张表各自的存在性"。
3. **加索引**：配合查询形态补索引（注意复合索引的最左前缀）。
4. **缓存**：对几乎不变的数据（如组织树）做短 TTL 内存缓存；对实时数据（如在线人数）**不要**缓存。

### 5.3 注意事项

- **改查询必须证口径等价**：任何查询改写，都要确认返回的业务数字和原来一致，否则就是"优化了个寂寞，还错了数"。
- **不要为了性能破坏架构**：共享的通用查询方法被多个模块复用，不要在热路径里为它单独造一套逻辑而不管别处——除非确认这是热点。

## 六、总结与展望

### 6.1 数据库查询优化的经验清单

从这次实践里沉淀出的、可以带到下一个项目去的教训：

1. **先量化，再动手**。凭感觉加缓存/索引经常无效。第一步永远是：把接口触发的每条 SQL 拉出来，数清楚**往返次数**；再用慢日志 / EXPLAIN 看**单条成本**。两个维度要分开看——「次数」是网络往返的开销，「单条成本」是扫描行数与传输量的开销，瓶颈可能在任意一头。
2. **"判存在"和"取数据"是两种活**。只想知道"有没有"，用 `EXISTS`/`Any()`，命中即停；要真正拿数据，才 JOIN / IN。这次 5 张材料表的判定全是"判存在"，却被实现成了"整表拉回内存再 `Distinct`"——活干错了形态。
3. **`.AsEnumerable()` 是整表拉回的警报**。ORM 翻译不了你的表达式（比如反射取属性），就会退化成"先全量查回来、再内存过滤"。凡是能下推 SQL 的过滤，都别让它落到内存里做。
4. **先减往返，再谈并行**。并行不减少查询次数，只减少墙钟耗时，还要多占连接。合并查询（6→1）是纯收益；并行是"用资源换时间"，优先级靠后。
5. **善用"已经算出来的中间结果"**。`workerIds` 是一次性算出的权威集合，下游全部拿 id 查。谁要是再重复判断"是不是在场的建筑工人"，谁就是重复劳动——重复查询往往藏在你最容易忽视的"顺手再查一遍"里。
6. **缓存要分数据性质**。几乎不变的数据（组织树、字典）值得短 TTL 缓存；实时数据（在线人数、状态、绑定关系）缓存了就是骗自己，数字一冻住反而更糟。
7. **索引是配套的，不是越多越好**。查什么形态，配什么索引；复合索引记住**最左前缀**。加完索引要验证是否真的被查询用上了（EXPLAIN 看执行计划），否则只是心理安慰。
8. **改查询必须证口径等价**。优化完数字变了，那不是优化是事故。用测试库逐字段比对 + 把关键查询暴露成 internal 写 SQL 翻译断言，锁住"单条查询 + EXISTS"这个形态，防止有人以后改回逐表查。

### 6.2 提速手段一览

按"改在哪一层"来分，比按"减什么"更实用——因为你着手时是站在某一层去动手的：

| 层面 | 手段 | 典型做法 | 主要收益 |
|---|---|---|---|
| ① ORM/代码层（优先） | 减少往返 | 合并查询、复用已算出的 id 集合、批量 `IN` 一把查 | 省网络往返 |
| ① ORM/代码层 | 避免客户端求值 | 判存在用 `Any()`/`Exists`，警惕 `.AsEnumerable()` 整表拉回 | 省内存与传输 |
| ① ORM/代码层 | 只取所需 | 只 `Select` 需要的列、分页 `Take/Skip` | 省传输与扫描 |
| ① ORM/代码层 | 只读跟踪 | 只读查询加 `AsNoTracking()` | 省 EF 跟踪开销 |
| ① ORM/代码层 | 并行化 | 各查询独立连接/DbContext | 省墙钟耗时 |
| ② 数据库层 | 索引 | 复合索引匹配查询形态（注意最左前缀）、覆盖索引 | 省扫描 |
| ② 数据库层 | SQL 形态 | EXISTS 判存在、JOIN 合并、避免函数包着索引列 | 省扫描 / 省往返 |
| ③ 应用层 | 缓存 | IMemoryCache / Redis 短 TTL（仅几乎不变的数据） | 省整段查询 |
| ③ 应用层 | 预计算 | 聚合计数缓存、物化统计 | 高频统计省查询 |
| ④ 架构层（最后） | 读写分离 | 主从、只读副本 | 分摊读压力 |
| ④ 架构层 | 冷热分离 | 历史数据归档到冷库 | 热表变小 |
| ④ 架构层 | 分区 / 分表 | 按时间、租户分区 | 超大表可控 |

**建议的执行顺序**：先做 ① 代码层（零成本、低风险、收益最直接），再做 ② 数据库层（低风险、需建索引），再评估 ③ 缓存（要考虑一致性），最后才考虑 ④ 架构层（成本最高）。本次案例就是典型的"先在 ① 拿到大头"。

### 6.3 不同场景下的取舍

优化手段没有银弹，关键看场景：

| 场景 | 怎么取舍 |
|---|---|
| 数据量小（几百行） | 整表拉回影响不大，别过度优化；但口径不能改 |
| 数据量大 / 高频接口 | 全力下推 SQL + 索引 + 合并查询；缓存值得投入 |
| 实时性敏感（在线人数） | 不缓存、不预计算；靠查询本身够快 |
| 多张异构表"判存在" | 相关 EXISTS 一次问完，别逐表各查 |
| 连接池紧张 / 高并发 | 慎用并行（每路占一个连接）；优先合并减少总次数 |
| 统计口径敏感 | 正确性优先，优化必须证等价；口径变更走评审 |

### 6.4 核心要点回顾

- 一次统计接口实际查了 **13 次数据库**，而非直觉上的几次；最重的单个指标占了 6 次。
- 慢的根源不只是"次数多"，还有 `AsEnumerable` 导致的**整表拉回内存**。
- 用一条相关 EXISTS 查询，把入场判定从 6 次往返压到 1 次，同时消灭了全表拉取，**语义严格等价、零风险纯收益**。
- 性能优化的正确姿势：**量化 → 定位 → 去重/合并 → 证等价 → 留测试**。

### 6.5 未来发展方向

- 为高频查询补索引（`person_id` 前缀、`project_id` 前缀等），进一步降低单条扫描成本。
- 对几乎不变的组织数据做短 TTL 缓存。
- 若有吞吐要求，再把彼此独立的查询并行化（各用独立 DbContext）。
- 后续需求若保证"项目人员必有组织关联"，可整段移除组织范围过滤查询。
